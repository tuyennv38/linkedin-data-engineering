# Streaming Ingestion vào Apache Iceberg: Giải bài toán "Small Files" và Xung đột Commit với Decoupled Compaction

"Pipeline Flink streaming ghi vào Iceberg chạy mượt mà suốt tuần đầu, nhưng sang tuần thứ hai, dashboard Trino và Superset bắt đầu timeout. Scan time từ 2 giây vọt lên hơn 45 giây dù lượng dữ liệu mỗi ngày không hề tăng."

Nếu đang vận hành kiến trúc Streaming Data Lakehouse với Apache Iceberg, rất có thể bạn đã từng đối mặt với kịch bản này. Phản xạ tự nhiên của nhiều đội ngũ là tăng RAM/CPU cho coordinator của Trino, hoặc vội vã trigger một lệnh gom file thủ công. Nhưng chỉ sau vài giờ, mọi thứ lại đâu vào đấy, thậm chí job streaming còn bị văng lỗi `CommitFailedException`.

Bản chất gốc rễ của vấn đề nằm ở đâu, và làm thế nào để thiết lập một cơ chế Compaction chuẩn Production mà không làm gián đoạn luồng Ingestion thời gian thực?

---

### 1. Bản chất của "Small Files" và Cơn ác mộng Metadata Bloat

Khi sử dụng Apache Flink hoặc Spark Structured Streaming để ghi dữ liệu vào Apache Iceberg với tần suất checkpoint ngắn (1–5 phút):
- **Ở tầng Storage**: Để đảm bảo tính nhất quán ACID của mỗi checkpoint, writer buộc phải đóng (flush) các buffer hiện tại và commit ra các data file Parquet mới. Kết quả là hàng chục nghìn file Parquet siêu nhỏ (chỉ từ vài chục KB đến vài MB) rải rác khắp các partition. Định dạng Parquet bị vô hiệu hóa các thế mạnh cốt lõi như dictionary encoding, run-length encoding và vectorization read vì footer của file nhỏ đã chiếm phần lớn dung lượng.
- **Ở tầng Metadata (Metadata Bloat)**: Mỗi commit tạo ra một Snapshot mới trỏ tới Manifest List, bên trong chứa hàng loạt Manifest Files với chi tiết min/max column bounds của từng data file. 
- **Cái giá phải trả khi Query**: Khi Trino hoặc Spark SQL thực hiện Scan Planning, engine tốn tới 80–90% thời gian để gửi hàng chục vạn API call (`GET/HEAD Object`) lên Object Storage (S3/GCS), tải và giải nén các Avro manifest chỉ để xác định cần đọc file nào. Thời gian mở file (file open overhead) hoàn toàn lấn át thời gian đọc dữ liệu thực tế.

### 2. Kiến trúc Decoupled Maintenance: Tách biệt Ingest và Compaction

Sai lầm phổ biến là cấu hình in-line compaction chạy trực tiếp bên trong Flink Streaming Ingestion pipeline. Việc này khiến TaskManager vừa phải xử lý stream, vừa phải gánh tải I/O nặng khi gom file, dễ dẫn đến nghẽn checkpoint (checkpoint timeout) và crash toàn bộ pipeline.

Giải pháp chuẩn cho môi trường Production là **Kiến trúc Decoupled Maintenance** (Tách rời bảo trì độc lập):

```
[Kafka / Kinesis] 
       │
       ▼
[Apache Flink Stream Job] ──(Micro-batch Commit 1-2m / MoR)──► [Iceberg Table on S3/MinIO]
                                                                  ▲   (Small Files + Deletes)
                                                                  │
[Airflow / Temporal Trigger] ──► [Spark Maintenance Worker] ──────┘
                                  - rewrite_data_files (BinPack/Sort)
                                  - rewrite_manifests
                                  - expire_snapshots
                                                                  │
                                                                  ▼
                                                      [Trino / StarRocks / Athena]
                                                      (Quét Clean Files 128MB - 256MB)
```

Kiến trúc này vận hành dựa trên 3 nguyên lý cốt lõi của Apache Iceberg:

#### a. Kiểm soát đồng thời lạc quan (OCC) và Cơ chế Auto-Retry
Trong Iceberg, luồng streaming ingestion thực hiện thao tác `AppendFiles` (hoặc `RowDelta`), chỉ bổ sung file mới vào snapshot. Trong khi đó, Spark Compaction Worker thực hiện thao tác `RewriteFiles` (thay thế tập small files cũ bằng consolidated files mới). 

Nhờ cơ chế Optimistic Concurrency Control (OCC) với Atomic Swap trên Catalog, khi Compaction commit, Iceberg kiểm tra: nếu các file mà Compaction vừa thay thế vẫn còn nguyên vẹn trong snapshot mới nhất, transaction sẽ tự động rebase và commit thành công mà không gây xung đột với các commit append mới từ Flink. Đối với các tranh chấp metadata tức thời tại catalog lock, cấu hình `'commit.retry.num-retries' = '10'` sẽ giúp các transaction tự động thử lại một cách an toàn mà không làm rớt pipeline.

#### b. Giữ Sequence Number gốc (`use-starting-sequence-number`)
Với bảng sử dụng cơ chế Merge-on-Read (MoR), nếu luồng streaming phát sinh Equality Deletes đồng thời trong lúc Spark đang chạy compaction:
- Mặc định thủ tục `rewrite_data_files` bật `use-starting-sequence-number = true`.
- Các file sau khi compact sẽ giữ nguyên `data_sequence_number` tại thời điểm bắt đầu compaction, thay vì gán sequence number mới.
- **Ý nghĩa sống còn**: Các Equality Deletes được commit sau đó (có sequence number lớn hơn) vẫn tiếp tục có hiệu lực lọc chính xác trên các compacted data files mới, loại bỏ hoàn toàn nguy cơ sai lệch dữ liệu hoặc commit fail.

#### c. Commit từng phần (Partial Progress)
Thay vì gom 100.000 file trong một transaction khổng lồ dễ gây tràn bộ nhớ (OOM), cấu hình `partial-progress.enabled = true` cho phép chia nhỏ quá trình compaction thành nhiều file group độc lập và commit lũy tiến. Nếu một group gặp lỗi, các group đã commit trước đó vẫn được bảo toàn.

### 3. Kịch bản Triển khai Thực chiến

#### Bước 1: Thiết lập Table Properties tối ưu từ đầu
Áp dụng DDL để Iceberg tự động tối ưu cấu trúc file, kích hoạt tính năng v2 và cơ chế retry khi tranh chấp:

```sql
ALTER TABLE prod_catalog.telemetry.events SET TBLPROPERTIES (
    -- Bắt buộc kích hoạt Iceberg v2 để hỗ trợ Row-level deletes (Merge-on-Read)
    'format-version' = '2',

    -- Kích thước data file mục tiêu (256MB là điểm cân bằng lý tưởng cho Object Storage)
    'write.target-file-size-bytes' = '268435456',

    -- Chế độ Merge-on-Read giảm write amplification cho streaming
    'write.delete.mode' = 'merge-on-read',
    'write.update.mode' = 'merge-on-read',
    'write.merge.mode'  = 'merge-on-read',

    -- Tự động retry commit lên Catalog khi xảy ra tranh chấp snapshot đồng thời
    'commit.retry.num-retries' = '10',

    -- Kích thước manifest file mục tiêu để tối ưu scan planning
    'commit.manifest.target-size-bytes' = '8388608', -- 8 MB

    -- Tự động gộp manifest lists nhỏ khi commit
    'commit.manifest-merge.enabled' = 'true'
);
```

#### Bước 2: Kịch bản Spark SQL Maintenance Pipeline (Chạy qua Airflow/Temporal)

**1. Compaction nhanh cho các partition đang active (Chạy mỗi 1 - 2 giờ):**
Sử dụng chiến lược `binpack` nhẹ nhàng, map-only để triệt tiêu small files mà không tốn chi phí shuffle mạng.

```sql
CALL prod_catalog.system.rewrite_data_files(
    table => 'prod_catalog.telemetry.events',
    strategy => 'binpack',
    options => map(
        'target-file-size-bytes', '268435456', -- 256 MB
        'min-file-size-bytes', '67108864',      -- Nhỏ hơn 64MB mới gom
        'max-file-size-bytes', '335544320',     -- Lớn hơn 320MB sẽ tách
        'min-input-files', '5',                 -- Tối thiểu 5 file nhỏ mới kích hoạt
        'max-concurrent-file-group-rewrites', '8',
        'partial-progress.enabled', 'true',
        'partial-progress.max-commits', '10',
        'use-starting-sequence-number', 'true'
    ),
    where => "event_date >= current_date() - interval 2 days"
);
```

**2. Compaction sâu với Sort/Z-Order cho partition đã đóng (Chạy ban đêm/hàng tuần):**
Áp dụng trên dữ liệu lịch sử không còn streaming ghi vào để tối ưu triệt để Data Skipping cho các câu query BI phức tạp.

```sql
CALL prod_catalog.system.rewrite_data_files(
    table => 'prod_catalog.telemetry.events',
    strategy => 'sort',
    sort_order => 'zorder(device_id, event_type)',
    options => map(
        'target-file-size-bytes', '536870912', -- 512 MB cho cold partition
        'rewrite-all', 'true'
    ),
    where => "event_date = current_date() - interval 7 days"
);
```

**3. Tối ưu Manifests và Dọn dẹp Snapshots cũ:**
Giúp metadata catalog gọn gàng và giải phóng các data file mồ côi trên S3. 

*Lưu ý về cú pháp*: Trong Spark SQL, tham số `older_than` của `CALL expire_snapshots` yêu cầu giá trị timestamp literal (thường được inject động qua biến macro của orchestrator, ví dụ `TIMESTAMP '{{ macros.ds_add(ds, -3) }} 00:00:00'` trong Apache Airflow).

```sql
-- Gộp các file manifest nhỏ thành manifest chuẩn
CALL prod_catalog.system.rewrite_manifests(
    table => 'prod_catalog.telemetry.events',
    use_caching => false
);

-- Xóa snapshots cũ hơn 3 ngày, giữ lại tối thiểu 50 snapshot gần nhất
CALL prod_catalog.system.expire_snapshots(
    table => 'prod_catalog.telemetry.events',
    older_than => TIMESTAMP '2026-10-16 00:00:00',
    retain_last => 50,
    max_concurrent_deletes => 16,
    stream_results => true -- Tránh tràn bộ nhớ (OOM) trên Spark Driver khi xóa lượng lớn file
);
```

### 4. Phân tích Đánh đổi: BinPack vs. Sort vs. Z-Order

Không có chiến lược nào là "viên đạn bạc" cho mọi tình huống:

| Tiêu chí | `binpack` | `sort` (Tuyến tính) | `z-order` / `hilbert` |
| :--- | :--- | :--- | :--- |
| **Bản chất** | Gom file theo kích thước (First-Fit-Decreasing) | Sắp xếp toàn bộ dòng theo thứ tự cột | Ánh xạ không gian đa chiều (Z-curve) |
| **Chi phí Compute / Shuffle** | **Rất thấp** (Map-only, không shuffle qua mạng) | **Trung bình - Cao** (Bắt buộc shuffle dữ liệu giữa executor) | **Rất cao** (Shuffle lớn kèm chi phí tính toán toán học trên CPU) |
| **Hiệu quả Data Skipping** | Thấp (chỉ giải quyết số lượng file) | **Cực cao trên cột đầu tiên** (Ví dụ lọc theo `user_id`) | **Cực cao trên 2 - 4 cột** được truy vấn kết hợp |
| **Thời gian thực thi** | Nhanh hơn 3x – 10x so với Sort | Trung bình | Lâu nhất |
| **Tần suất khuyến nghị** | **Hourly** trên active streaming partitions | **Daily / Weekly** trên closed partitions | **Weekly / Monthly** trên các bảng ad-hoc analytics |

*Lưu ý sống còn về Snapshot Expiration & Downstream CDC Readers*: 
Việc thu hẹp retention (ví dụ `< 24h`) giúp dọn dẹp dung lượng S3 nhanh chóng và giảm tải metadata. Tuy nhiên, nếu hệ thống có các downstream consumer đọc dữ liệu incremental/CDC từ Iceberg (như Spark Structured Streaming hoặc Debezium Iceberg connector) bị lag vượt quá ngưỡng retention, các reader này sẽ lập tức crash với lỗi `FileNotFoundException` do commit snapshot và data file tương ứng đã bị xóa vĩnh viễn. Hãy đảm bảo retention window luôn lớn hơn SLA xử lý lỗi tối đa của các streaming readers.

### 5. Bài học Thực chiến từ Kinh nghiệm Sản xuất

1. **Phân tầng Compaction (Tiered Maintenance)**: Đừng lạm dụng Sort/Z-Order cho các partition đang có dữ liệu streaming đổ về liên tục. Hãy áp dụng công thức: `BinPack` chạy tần suất cao để dập tắt small files ngay tại tầng nóng; `Sort/Z-Order` chạy định kỳ ngoài giờ cao điểm ở tầng dữ liệu đã đóng.
2. **Tuyệt đối tách riêng luồng Ingest và Compaction**: Đừng bắt worker streaming làm nhiệm vụ dọn dẹp storage. Việc tách độc lập giúp bảo vệ SLA ingestion 24/7.
3. **Cấu hình bảng chuẩn Iceberg v2 ngay từ đầu**: Đảm bảo khai báo `'format-version' = '2'` cùng cơ chế retry để hỗ trợ trơn tru Merge-on-Read và giải quyết tranh chấp snapshot.
4. **Hiệu quả đã được thực chứng**: Trong báo cáo kỹ thuật từ Netflix Engineering về giải pháp AutoOptimize trên Iceberg, việc áp dụng compaction có chọn lọc và phân tầng đã giúp **giảm 80% tổng số lượng file**, **giảm 22% partition scans**, qua đó **tăng tốc độ truy vấn lên tới 60%** và **tiết kiệm 70% chi phí compute** so với cơ chế merge định kỳ truyền thống.

- **Required data flow**:
  1. *Real-time Write Lane*: `Kafka` -> `Flink Ingest` -> tạo liên tục `Small Files + Deletes (MoR)` trên S3.

  3. *Read Lane*: `Trino / StarRocks` query snapshot mới nhất -> scan planning siêu tốc qua consolidated manifests và data files chuẩn.
