# Kế hoạch nội dung: 2026-10-18

- **Topic**: Giải quyết bài toán Deduplication và Out-of-Order CDC Events khi ingest từ PostgreSQL vào ClickHouse
- **Target audience**: Senior Data Engineers, Backend Engineers, Data Platform Leads
- **Problem statement**: Khi sync dữ liệu realtime CDC từ PostgreSQL qua Kafka vào ClickHouse, việc mạng chập chờn hoặc retry khiến event bị duplicate và đến sai thứ tự (out-of-order). Dùng `ReplacingMergeTree` thông thường không đảm bảo kết quả chính xác tức thì (eventual consistency) nếu chưa chạy optimize merge.
- **Unique angle**: So sánh thực tế giữa `ReplacingMergeTree` với `argMax()` query pattern và kiến trúc versioning sử dụng `CollapsingMergeTree` để đạt zero-duplicate realtime analytics mà không tốn tài nguyên background merge.
- **Key takeaways**:
  1. Hiểu rõ cơ chế asynchronous merge của `ReplacingMergeTree` và tại sao không nên lạm dụng `FINAL`.
  2. Cách tận dụng `_version` column và hàm `argMax()` trên ClickHouse để truy vấn dữ liệu mới nhất tức thì.
  3. Mô hình Idempotent Consumer kết hợp Kafka Engine & Materialized View.
- **Suggested architecture/example**:
  PostgreSQL (Wal2json/Debezium) -> Apache Kafka -> ClickHouse Kafka Engine -> Materialized View -> ReplacingMergeTree Target Table -> BI/API Query (via argMax).
- **Research questions**:
  1. Hiệu năng của `FINAL` modifier trong các phiên bản ClickHouse gần đây (từ 23.x trở lên) đã được tối ưu ra sao?
  2. Sự khác biệt về CPU/RAM giữa `argMax()` aggregation và `FINAL` khi scan bảng hàng trăm triệu dòng.
  3. Cách Debezium tạo snapshot version (lsn / ts_ms) để ClickHouse làm căn cứ versioning.
- **Suggested diagram**: Flowchart LR thể hiện luồng CDC từ PG -> Kafka -> Kafka Engine Table -> Materialized View -> Base Table (kèm cơ chế deduplication logic).
- **Suggested cover image**: Minh họa luồng dữ liệu stream màu neon công nghệ đi qua bộ lọc deduplication vào một database siêu tốc độ ClickHouse (isometric 3D style, dark modern UI).
