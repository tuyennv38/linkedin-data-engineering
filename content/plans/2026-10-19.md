# Kế hoạch nội dung: 2026-10-19

- **Topic**: Giải quyết bài toán "Small Files Problem" và tối ưu Compaction khi Streaming Ingestion vào Apache Iceberg
- **Target audience**: Data Engineers, Data Architects, Platform Engineers, Tech Leads
- **Problem statement**: Khi ingest dữ liệu streaming tần suất cao (micro-batching 1–5 phút qua Apache Flink hoặc Spark Streaming) vào Apache Iceberg, hệ thống liên tục sinh ra hàng nghìn data files Parquet dung lượng nhỏ (vài KB đến vài MB). Điều này dẫn đến bùng nổ metadata manifest files, gây suy giảm nghiêm trọng hiệu năng query của các engine (Trino, Spark, StarRocks) do overhead mở file và bão hòa I/O requests lên Object Storage (S3/GCS), đồng thời dễ gây xung đột commit (commit conflict) nếu trigger compaction cùng lúc với streaming write.
- **Unique angle**: Không chỉ dừng lại ở việc chạy thủ công thủ tục `rewrite_data_files`, kế hoạch đi sâu vào thiết kế kiến trúc phân tách độc lập (decoupling) giữa luồng Streaming Ingestion và luồng Maintenance Compaction Worker. So sánh thực tế giữa Bin-packing (nhẹ CPU, gom nhanh) vs Sort/Z-Order (tối ưu data skipping cho query), cùng giải pháp xử lý Optimistic Concurrency Control (OCC) retry để streaming write không bao giờ bị fail commit.
- **Key takeaways**:
  1. Hiểu rõ nguyên nhân gốc rễ vì sao streaming micro-batching dẫn đến "Small Files & Metadata Bloat" trên Lakehouse.
  2. So sánh 2 chiến lược compaction chính trong Iceberg: Bin-packing (ưu tiên throughput ghi) vs Sort-order / Z-Order (ưu tiên tốc độ scan truy vấn).
  3. Thiết kế kiến trúc Decoupled Maintenance: Tách riêng Flink/Spark Ingestion và Orchestrated Compaction Job (Airflow / Temporal / Iceberg REST Catalog triggers) để triệt tiêu commit conflict.
  4. Bộ quy tắc cấu hình thực chiến (Best Practices): Kích thước target file lý tưởng (128MB – 512MB), tần suất chạy `rewrite_manifests`, quản lý `snapshot retention` và dọn dẹp `orphan files`.
- **Suggested architecture/example**:
  Kafka / Kinesis -> Apache Flink (Streaming Ingestion với Merge-on-Read, checkpoint/commit 1–2 phút) -> S3/MinIO Data Lake (Raw small Parquet files & Equality deletes) -> Decoupled Spark Compaction Job (Scheduled via Airflow/Temporal chạy `rewrite_data_files` bin-packing & `rewrite_manifests`) -> Optimized Target Parquet Files (128MB–256MB) -> Trino / Athena / Spark SQL Query Engine.
- **Research questions**:
  1. Cơ chế Optimistic Concurrency Control (OCC) của Apache Iceberg xử lý conflict ra sao khi `rewrite_data_files` commit cùng lúc với Flink streaming commit?
  2. Benchmark thực tế mức độ suy giảm query latency (scan time) giữa một bảng Iceberg có 10.000 small files và sau khi được compact thành ~100 files chuẩn 128MB.
  3. Khi nào nên dùng Bin-packing và khi nào nên đầu tư tài nguyên compute cho Sort-order / Z-ordering trong quá trình rewrite data files?
- **Suggested diagram**: Flowchart/Architecture diagram thể hiện 2 luồng phân tách độc lập: Luồng Write Real-time (Kafka -> Flink -> Small Parquet files + Manifests) và Luồng Maintenance Decoupled (Scheduled Spark Job -> Compaction / Bin-packing -> Consolidated Parquet Files -> Dọn dẹp metadata cũ), bên dưới là Read Engine (Trino/Athena) quét dữ liệu đã được tối ưu.
- **Suggested cover image**: Minh họa 3D isometric phong cách công nghệ hiện đại, nền tối (dark UI): Dòng dữ liệu li ti (small files) màu neon cyan đổ liên tục qua một cỗ máy xử lý thông minh (Compaction Engine) và được gom tụ, tinh chỉnh thành các khối dữ liệu hình lập phương / lục giác vững chắc, phát sáng tối ưu tốc độ truy vấn.
