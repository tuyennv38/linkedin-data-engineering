# Apache Iceberg Small Files Problem & Compaction Architecture in Streaming Ingestion

- **Topic**: Giải quyết bài toán "Small Files Problem" và tối ưu Compaction khi Streaming Ingestion vào Apache Iceberg.
- **Ngày nghiên cứu**: 2026-10-18 / 2026-10-19.
- **Phân loại**: Data Lakehouse Architecture, Storage Maintenance, Concurrency Control.

---

## 1. Technical Findings

### 1.1. Bản chất của "Small Files Problem" & Metadata Bloat trong Streaming Ingestion
- **Cơ chế streaming writes**: Khi các engine như Apache Flink hoặc Spark Structured Streaming ingest dữ liệu liên tục với tần suất checkpoint ngắn (1–5 phút), mỗi chu kỳ commit checkpoint bắt buộc phải đóng (flush) các buffer file hiện tại và tạo ra các data file Parquet mới để đảm bảo tính nhất quán (ACID).
- **Hệ quả ở Storage Layer**:
  - Dữ liệu rải rác: Hàng chục đến hàng trăm file Parquet siêu nhỏ (kích thước từ vài chục KB đến vài MB) được tạo ra mỗi giờ cho mỗi partition.
  - Phá vỡ tối ưu của columnar format: Parquet phát huy tối đa hiệu quả nén (dictionary encoding, run-length encoding) và I/O vectorization khi row-group đạt kích thước chuẩn (128MB - 512MB). File nhỏ khiến footer Parquet chiếm tỷ lệ % dung lượng đáng kể, giảm tỷ lệ nén (compression ratio).
- **Hệ quả ở Metadata Layer**:
  - Mỗi commit sinh ra 1 Snapshot mới, trỏ tới một Manifest List file.
  - Manifest List chứa danh sách các Manifest Files; mỗi Manifest File lại chứa danh sách chi tiết các Data Files kèm metadata thống kê (min/max column bounds, null counts, file size).
  - Khi số lượng file lên tới hàng trăm nghìn hoặc hàng triệu, metadata footprint phình to (Metadata Bloat). Khi Trino/Spark lập kế hoạch truy vấn (Query Planning / Scan Planning), engine phải tải hàng nghìn manifest files, giải nén Avro metadata và duyệt qua hàng triệu file entries để thực hiện partition/column pruning.
  - Query latency tăng vọt không phải do thời gian đọc dữ liệu (data scan) mà do thời gian mở file (file open cost), latency của API call lên Object Storage (`GET / HEAD Object` trên S3/GCS), và thời gian Scan Planning ở Query Engine Driver/Coordinator.

### 1.2. Cơ chế Optimistic Concurrency Control (OCC) & Conflict Resolution
Apache Iceberg áp dụng mô hình kiểm soát đồng thời lạc quan (OCC) với Atomic Swap trên Catalog (như Iceberg REST Catalog, DynamoDB Catalog, AWS Glue, hoặc Hive Metastore):

1. **Phân loại thao tác commit**:
   - **Streaming Ingestion**: Sử dụng thao tác `AppendFiles` hoặc `RowDelta` (khi có Upsert/Delete). Writer chỉ thêm các file mới vào snapshot mới mà không xóa/sửa đổi file cũ đã commit.
   - **Compaction**: Sử dụng thao tác `RewriteFiles`. Writer đọc một tập hợp các small data files (hoặc delete files), gom lại thành các file mới lớn hơn, sau đó commit một snapshot mới với hành động: *xóa các small data files cũ và thêm các consolidated data files mới*.

2. **Cơ chế phát hiện xung đột (File-Level Conflict Detection)**:
   - Khi compaction job hoàn tất việc ghi các file mới, nó gửi yêu cầu commit `RewriteFiles` lên Catalog.
   - Trong lúc compaction đang chạy, Flink/Spark streaming có thể đã commit nhiều snapshot mới (ví dụ 10 checkpoint = 10 snapshot appends).
   - Iceberg Catalog thực hiện kiểm tra: Compaction so sánh snapshot hiện tại của bảng với `starting_snapshot` của compaction.
   - **Nếu writer đồng thời chỉ thực hiện Append (thêm data files mới)**: Compaction re-base các thay đổi của mình trên snapshot mới nhất và commit thành công mà **không gặp xung đột**, vì các data files mà compaction vừa thay thế vẫn còn nguyên vẹn trong snapshot mới nhất.
   - **Nếu writer đồng thời thực hiện xóa/thay đổi chính các file mà compaction đang rewrite**: Iceberg sẽ ném ra ngoại lệ `ValidationException` / `CommitFailedException` vì tập file gốc bị rewrite đã không còn tồn tại ở trạng thái mong đợi.

3. **Cơ chế Sequence Number với Merge-on-Read (`use-starting-sequence-number`)**:
   - Mặc định trong Iceberg Spark Procedure `rewrite_data_files`, tham số `use-starting-sequence-number = true`.
   - Các file dữ liệu mới sau khi compact sẽ giữ nguyên `data_sequence_number` của snapshot tại thời điểm bắt đầu compaction (starting snapshot), thay vì gán sequence number mới toanh tại thời điểm commit compaction.
   - **Ý nghĩa sống còn**: Nếu trong lúc compaction chạy, streaming pipeline commit thêm các **Equality Delete files** mới (có sequence number cao hơn starting snapshot), các equality deletes này vẫn tiếp tục có hiệu lực lọc trên các compacted data files mới, ngăn chặn hoàn toàn nguy cơ mất dữ liệu hoặc sai lệch tính đúng đắn, đồng thời không gây xung đột commit.

4. **Kỹ thuật Partial Progress Commits**:
   - Nếu bảng có 100.000 files, việc chạy 1 compaction transaction gom toàn bộ 100.000 files sẽ tiềm ẩn rủi ro OOM và tăng nguy cơ conflict sau nhiều giờ chạy.
   - Iceberg hỗ trợ `partial-progress.enabled = true` cùng `partial-progress.max-commits = 10`. Quá trình compaction chia dữ liệu thành nhiều file groups độc lập và commit lần lượt từng group. Nếu 1 group bị fail hoặc conflict, các file groups đã commit trước đó vẫn được bảo toàn.

### 1.3. Phân tích các Chiến lược Compaction: `binpack` vs `sort` vs `z-order`

| Tiêu chí | `binpack` (Mặc định) | `sort` (Linear Sort) | `z-order` / `hilbert` |
| :--- | :--- | :--- | :--- |
| **Bản chất thuật toán** | First-Fit-Decreasing: Gom các file nhỏ theo kích thước để nhét đầy `target-file-size`. | Sắp xếp dữ liệu theo thứ tự tuyến tính của 1 hoặc nhiều cột (`ORDER BY col1, col2`). | Ánh xạ không gian đa chiều (Z-order space-filling curve) trên nhiều cột. |
| **Chi phí Compute / Shuffle** | **Rất thấp**: Không yêu cầu shuffle dữ liệu giữa các Spark executor. Chạy dạng map-only/partition-local. | **Trung bình - Cao**: Bắt buộc shuffle toàn bộ dữ liệu theo sort keys để sắp xếp trước khi ghi. | **Rất cao**: Cần shuffle dữ liệu và tính toán đường cong Z-curve / Hilbert curve phức tạp trên CPU. |
| **Tác động lên Data Skipping** | **Thấp**: Chỉ gom file, min/max bounds của các cột trong manifest không được thu hẹp, độ chồng lấn (overlapping) giữa các file vẫn cao. | **Rất cao (Đơn chiều)**: Phù hợp tối đa cho các truy vấn filter theo cột đầu tiên của sort order (ví dụ: `event_time`, `user_id`). | **Rất cao (Đa chiều)**: Cung cấp khả năng skipping đồng đều trên 2-4 cột lọc độc lập (ví dụ vừa filter `tenant_id`, vừa filter `event_type`, vừa filter `timestamp`). |
| **Thời gian thực thi** | Nhanh hơn 3x – 10x so với sort. | Chậm hơn, phụ thuộc băng thông network shuffle của cụm Spark. | Chậm nhất trong 3 chiến lược. |
| **Khuyến nghị sử dụng** | Chạy thường xuyên theo chu kỳ (ví dụ mỗi 30-60 phút) ở tầng bronze/silver để dập tắt small files. | Chạy theo lịch hàng ngày/tuần trên các cột partition/clustering chính. | Áp dụng cho các bảng phân tích ad-hoc phức tạp nơi người dùng filter ngẫu nhiên trên nhiều chiều. |

### 1.4. Merge-on-Read (MoR) và Cơ chế Merge Deletes
- Trong Iceberg v2 table format, khi dữ liệu được update/delete trong streaming:
  - **Position Deletes**: Chứa đường dẫn file (file path) và vị trí index hàng (row position) cần xóa.
  - **Equality Deletes**: Chứa giá trị của cột khóa (ví dụ: `id = 12345`), áp dụng cho tất cả data files có sequence number nhỏ hơn hoặc bằng nó.
  - **Deletion Vectors (Iceberg v3)**: Lưu trữ dạng Roaring Bitmap trực tiếp trong metadata hoặc file phụ trợ để tối ưu kích thước.
- **Vấn đề khi đọc (Read Overhead)**: Khi Trino/Spark scan bảng MoR có nhiều delete files, engine phải load các delete files vào memory (Hash Set) để thực hiện Anti-Join / Filter tại thời điểm đọc. Nhiều delete files làm sụt giảm nghiêm trọng tốc độ query.
- **Compaction xử lý Deletes như thế nào**:
  - `rewrite_data_files` đọc cả data file và các delete files liên quan.
  - Nó áp dụng các delete files trực tiếp vào row-set trong bộ nhớ, loại bỏ triệt để các bản ghi đã xóa, và ghi ra **data files mới hoàn toàn "sạch"** (clean data files).
  - Thủ tục đồng thời giải phóng/xóa bỏ tham chiếu tới các position/equality delete files không còn cần thiết, khôi phục lại hiệu năng đọc tốc độ cao (tương đương Copy-on-Write) mà không làm chậm luồng ghi real-time ban đầu.

## 2. Architecture Options

### Lựa chọn 1: Decoupled Maintenance Worker (Khuyến nghị sản xuất)
- **Kiến trúc**:
  - **Luồng Ghi (Streaming Ingestion)**: Apache Flink đọc từ Kafka/Kinesis và ghi trực tiếp vào Iceberg Table qua `IcebergFilesCommitter` với commit interval 1–2 phút. Cấu hình bảng dùng Merge-on-Read (`write.delete.mode = 'merge-on-read'`).
  - **Luồng Bảo trì (Decoupled Spark Maintenance Job)**: Một cụm Spark riêng biệt (hoặc serverless EMR/Databricks job) được kích hoạt theo lịch bởi Orchestrator (Apache Airflow / Temporal) hoặc theo cơ chế Event-driven.
  - Worker này thực hiện tuần tự:
    1. `CALL system.rewrite_data_files(...)` với `binpack` cho các partition mới (vài giờ gần nhất).
    2. `CALL system.rewrite_manifests(...)` để gộp và sắp xếp lại manifest files.
    3. `CALL system.expire_snapshots(...)` định kỳ dọn dẹp các snapshot cũ và file rác.
- **Đánh giá**:
  - Tách rời hoàn toàn tài nguyên CPU/RAM giữa luồng streaming và luồng compaction.
  - Streaming ingestion không bao giờ bị nghẽn (backpressure) do compaction.

### Lựa chọn 2: In-line Compaction trong Flink Streaming Job
- **Kiến trúc**: Flink cung cấp tính năng Flink Table Maintenance / Post-commit compaction chạy ngay bên trong Flink application topology.
- **Đánh giá**:
  - Tiện lợi vì không cần duy trì cluster Spark riêng.
  - Tuy nhiên, cạnh tranh tài nguyên TaskManager trực tiếp với luồng ingest chính; nếu lượng dữ liệu dồn về lớn, compaction có thể chiếm CPU/I/O gây trễ checkpoint, sinh ra checkpoint timeout và crash pipeline streaming.
  - Chỉ phù hợp với bảng quy mô nhỏ hoặc vừa.

### Lựa chọn 3: Event-Driven Entropy Compaction (Mô hình Netflix AutoOptimize)
- **Kiến trúc**:
  - Ingestion ghi vào Iceberg.
  - Catalog gửi commit events vào Message Queue (SQS/Kafka).
  - Dịch vụ điều phối tính toán chỉ số phân mảnh (Partition Size Entropy). Chỉ khi partition bị trôi lệch khỏi ngưỡng tối ưu (đủ số lượng file nhỏ hoặc tỷ lệ delete files vượt quá ngưỡng) thì mới dispatch task cho worker pool xử lý.
- **Đánh giá**: Tối ưu chi phí compute cao nhất, loại bỏ việc quét mù toàn bộ bảng theo giờ.

## 3. Pros and Cons

| Thành phần / Giải pháp | Ưu điểm | Nhược điểm / Rủi ro |
| :--- | :--- | :--- |
| **Decoupled Spark Maintenance** | - Độc lập tài nguyên, không gây trễ streaming.<br>- Tận dụng sức mạnh xử lý song song phân tán của Spark cho compaction lớn.<br>- Hỗ trợ đầy đủ các chiến lược `binpack`, `sort`, `z-order`. | - Cần duy trì thêm cụm Spark và orchestrator (Airflow/Temporal).<br>- Tốn chi phí hạ tầng bổ sung. |
| **BinPack Strategy** | - Tốc độ chạy cực nhanh, tiêu thụ ít CPU/RAM.<br>- Không shuffle mạng.<br>- Giải quyết dứt điểm 90% bài toán small files cho streaming. | - Không tối ưu hóa được data layout cho các câu query có điều kiện lọc (filter predicates) phức tạp. |
| **Sort / Z-Order Strategy** | - Giảm tối đa dung lượng scan (Data Skipping vượt trội).<br>- Tăng tốc độ Trino/Athena query lên 50% - 80%. | - Rất tốn tài nguyên Spark (Shuffle I/O lớn).<br>- Thời gian chạy lâu, nguy cơ conflict cao hơn nếu chạy trên các partition đang có ghi liên tục. |
| **Aggressive Snapshot Expiration** | - Giải phóng dung lượng lưu trữ trên S3/MinIO nhanh chóng.<br>- Giảm kích thước metadata catalog. | - Thu hẹp cửa sổ Time Travel. Nếu đặt retention quá ngắn (ví dụ < 24h), các long-running queries hoặc CDC readers có thể bị lỗi `FileNotFoundException`. |

## 4. Verified Facts

1. **Hiệu quả thực tế từ Netflix Engineering**:
   - Theo công bố chính thức từ Netflix Technology Blog (*"Optimizing data warehouse storage"*), hệ thống AutoOptimize áp dụng compaction có chọn lọc trên Apache Iceberg đã giúp:
     - Giảm **80% tổng số lượng file** trên Data Warehouse.
     - Giảm **72% số lượng file replacements**.
     - Giảm **22% số lượng partition scans**.
     - Tăng tốc độ truy vấn lên tới **60%**.
     - Tiết kiệm **70% chi phí compute** so với cơ chế merge định kỳ truyền thống.
2. **Iceberg Spark Procedure `rewrite_data_files`**:
   - Tham số `strategy` mặc định là `binpack`. Hỗ trợ các tùy chọn `sort` (với `sort_order`) và `zorder(...)`.
   - Tham số `use-starting-sequence-number` mặc định là `true`, đảm bảo các equality delete mới hơn sequence number của compaction vẫn áp dụng chính xác cho các compacted files.
   - Hỗ trợ `partial-progress.enabled` cho phép commit từng phần (incremental commits), giảm thiểu rủi ro abort toàn bộ job khi xảy ra lỗi.
3. **Cơ chế Commit của Trino**:
   - Trino hỗ trợ compaction thông qua câu lệnh: `ALTER TABLE ... EXECUTE optimize(file_size_threshold => '128MB')`.
   - Trino cũng hỗ trợ gom metadata manifest thông qua `ALTER TABLE ... EXECUTE optimize_manifests`.
4. **Quy tắc Snapshot Isolation**:
   - `expire_snapshots` chỉ xóa các data files **chỉ thuộc về các snapshot đã hết hạn**. Nếu một data file vẫn được trỏ tới bởi ít nhất một snapshot còn hiệu lực (chưa expire), file đó tuyệt đối không bị xóa.

## 5. Unverified Claims / Cần lưu ý khi nhận định

1. *"Compaction không bao giờ bị commit conflict với Streaming Ingestion"*:
   - **Xác minh**: Nhận định này **chỉ đúng khi writer là Append-only**. Nếu luồng streaming là Upsert/Delete sử dụng Position Deletes hoặc rewrite file trực tiếp, và delete nhắm vào đúng các file đang bị compaction gom lại, compaction commit có thể bị fail với `ValidationException`. Do đó cần cấu hình retry hoặc áp dụng sequence number cô lập.
2. *"Z-Ordering luôn tốt hơn Sort tuyến tính"*:
   - **Xác minh**: Không chính xác. Nếu các câu truy vấn chủ yếu lọc theo 1 cột duy nhất (ví dụ `event_date` hoặc `tenant_id`), Sort tuyến tính đơn chiều luôn cho hiệu quả skipping và tốc độ nén vượt trội hơn Z-Ordering, đồng thời tốn ít chi phí shuffle hơn đáng kể. Z-Ordering chỉ có lợi khi có từ 2 đến 4 cột thường xuyên được filter kết hợp ngẫu nhiên.
3. *"Càng đặt target file size lớn thì query càng nhanh"*:
   - **Xác minh**: Không đúng. Nếu target file size quá lớn (ví dụ > 1GB), độ song song (parallelism) của query engine (Trino split generation) sẽ bị giảm, và bộ nhớ đệm của reader có thể bị áp lực. Kích thước tối ưu được khuyến nghị cho Object Storage phổ biến là **128MB đến 512MB**.

## 6. Code & SQL Examples

### 6.1. Cấu hình Iceberg Table Properties tối ưu cho Streaming & Compaction
Áp dụng DDL để thiết lập kích thước file mục tiêu và hành vi ghi:

```sql
ALTER TABLE prod_catalog.telemetry.events SET TBLPROPERTIES (
    -- Kích thước file dữ liệu mục tiêu khi write và rewrite (mặc định 512MB, streaming nên để 128MB - 256MB)
    'write.target-file-size-bytes' = '268435456', -- 256 MB

    -- Sử dụng Merge-on-Read cho streaming writes để giảm write latency
    'write.delete.mode' = 'merge-on-read',
    'write.update.mode' = 'merge-on-read',
    'write.merge.mode'  = 'merge-on-read',

    -- Ngưỡng kích thước file manifest tối ưu cho scan planning
    'commit.manifest.target-size-bytes' = '8388608', -- 8 MB

    -- Tự động dọn dẹp manifest lists khi commit
    'commit.manifest-merge.enabled' = 'true'
);
```

### 6.2. Kịch bản Spark SQL Maintenance Pipeline (Chạy qua Airflow / Cron)

#### Bước 1: Compaction Data Files (Bin-packing nhanh cho các partition đang hoạt động)
```sql
-- Chạy BinPack gom các small files < 64MB thành file chuẩn 256MB
-- Lọc chỉ xử lý các partition 3 ngày gần nhất để tránh quét toàn bộ bảng
CALL prod_catalog.system.rewrite_data_files(
    table => 'telemetry.events',
    strategy => 'binpack',
    options => map(
        'target-file-size-bytes', '268435456', -- 256 MB
        'min-file-size-bytes', '67108864',      -- Nhỏ hơn 64MB mới cần gom
        'max-file-size-bytes', '335544320',     -- Lớn hơn 320MB sẽ bị tách
        'min-input-files', '5',                 -- Chỉ gom nếu có từ 5 file nhỏ trở lên
        'max-concurrent-file-group-rewrites', '10',
        'partial-progress.enabled', 'true',     -- Commit từng đợt để tránh fail toàn bộ
        'partial-progress.max-commits', '10',
        'use-starting-sequence-number', 'true'  -- Giữ nguyên sequence number để tương thích MoR deletes
    ),
    where => "event_date >= current_date() - interval 3 days"
);
```

#### Bước 2: Compaction kết hợp Sort / Z-Order cho Cold/Historical Partitions (Chạy hàng tuần)
```sql
-- Tái cấu trúc dữ liệu theo Z-Order trên các partition đã đóng (không còn ghi streaming)
CALL prod_catalog.system.rewrite_data_files(
    table => 'telemetry.events',
    strategy => 'sort',
    sort_order => 'zorder(device_id, event_type)',
    options => map(
        'target-file-size-bytes', '536870912', -- 512 MB cho cold data
        'rewrite-all', 'true'
    ),
    where => "event_date = current_date() - interval 7 days"
);
```

#### Bước 3: Tối ưu hóa Metadata Manifests
```sql
-- Sắp xếp lại entries trong manifest files theo partition spec để tăng tốc scan planning
CALL prod_catalog.system.rewrite_manifests(
    table => 'telemetry.events',
    use_caching => false
);
```

#### Bước 4: Hết hạn Snapshots và Xóa Files rác
```sql
-- Giữ lại snapshot trong vòng 3 ngày, bảo tồn tối thiểu 50 snapshots gần nhất cho audit/time travel
CALL prod_catalog.system.expire_snapshots(
    table => 'telemetry.events',
    older_than => (current_timestamp() - interval 3 days),
    retain_last => 50,
    max_concurrent_deletes => 16,
    stream_results => true -- Tránh OOM trên Spark Driver khi số lượng file xóa lớn
);
```

### 6.3. Kịch bản Compaction trên Trino Engine
Nếu hệ thống sử dụng Trino làm engine thực thi bảo trì:

```sql
-- 1. Gom các file nhỏ dưới 100MB cho partition cụ thể
ALTER TABLE prod_catalog.telemetry.events 
EXECUTE optimize(file_size_threshold => '100MB')
WHERE event_date = CURRENT_DATE - INTERVAL '1' DAY;

-- 2. Gom manifest files trên Trino
ALTER TABLE prod_catalog.telemetry.events 
EXECUTE optimize_manifests;

-- 3. Xóa snapshots cũ hơn 3 ngày trên Trino
ALTER TABLE prod_catalog.telemetry.events 
EXECUTE expire_snapshots(retention_threshold => '3d');
```

## 8. Recommendations for the Writer

1. **Cấu trúc bài viết nên đi từ nỗi đau thực tế (Production Pain Points)**:
   - Mở đầu bằng kịch bản quen thuộc: Pipeline Flink streaming ghi vào Iceberg chạy rất mượt trong tuần đầu tiên, nhưng sang tuần thứ hai, dashboard Trino/Superset bắt đầu time-out, scan time từ 2 giây tăng vọt lên 45 giây dù volume dữ liệu mỗi ngày không đổi.
   - Giải thích nguyên nhân trực quan: Trino tốn 90% thời gian để list/open 50.000 file vài KB thay vì đọc dữ liệu thật.

2. **Làm nổi bật ranh giới giữa BinPack và Sort/Z-Order**:
   - Nhấn mạnh rằng **không nên lạm dụng Sort / Z-Order trong các job compaction chạy tần suất cao (hourly)** vì shuffle cost sẽ đốt cháy ngân sách compute của data platform.
   - Đưa ra công thức phân tầng:
     - **Tầng Hot (Real-time ingest, 0–24h)**: Chạy `binpack` nhẹ nhàng, map-only để triệt tiêu small files.
     - **Tầng Warm/Cold (Dữ liệu đã ổn định, > 24h)**: Chạy `sort` hoặc `z-order` theo lịch đêm để tối ưu hóa triệt để cho BI queries.

3. **Nhấn mạnh tầm quan trọng của `use-starting-sequence-number`**:
   - Đây là chi tiết kỹ thuật "ăn tiền" thể hiện trình độ Senior DE: Giải thích vì sao việc giữ sequence number của starting snapshot giúp compaction không làm mất hiệu lực của các equality deletes được ghi đồng thời bởi streaming writer.

4. **Trực quan hóa bằng sơ đồ kiến trúc Decoupled**:
   - Trong bài viết nên vẽ một diagram chia làm 2 làn (two lanes):
     - Làn trên: `Kafka -> Flink -> Iceberg (Small Files + Delete Files)`.
     - Làn dưới: `Airflow Trigger -> Spark Compaction Worker -> Consolidated Clean Files (128MB - 256MB)`.
     - Read Engine (Trino) luôn đọc snapshot mới nhất với latency tối ưu.

5. **Bộ checklist cấu hình mang tính hành động (Actionable Checklist)**:
   - Cung cấp sẵn các giá trị cấu hình mẫu: `write.target-file-size-bytes = 256MB`, `commit.manifest.target-size-bytes = 8MB`, `retain_last = 50`, `older_than = 3 days`.
